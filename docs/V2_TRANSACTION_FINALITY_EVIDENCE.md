# PrecedentOS 2.0 — Transaction Lifecycle Evidence

**Verification date:** 2026-10-14
**Pinned frontend package:** `genlayer-js 1.1.8`

## SDK interface confirmed from installed package source

The installed `genlayer-js@1.1.8` declaration and JavaScript implementation expose:

- `writeContract(...)` returning a transaction hash;
- `getTransaction({ hash })` returning stored transaction fields including `statusName` and execution result;
- `waitForTransactionReceipt({ hash, status, interval, retries })` (the v1.1.8 argument is `status`, not the newer documentation's `waitUntil` form);
- `TransactionStatus` names including `PENDING`, `PROPOSING`, `COMMITTING`, `REVEALING`, `ACCEPTED`, `UNDETERMINED`, `FINALIZED`, `CANCELED`, appeal phases, `READY_TO_FINALIZE`, and validator/leader timeout states;
- execution result names `NOT_VOTED`, `FINISHED_WITH_RETURN`, and `FINISHED_WITH_ERROR`.

The app's `trackTransactionLifecycle` implementation in `frontend/src/lib/genlayer/client.ts` therefore:

1. Reads the transaction after submission and keeps `ACCEPTED` visibly nonfinal.
2. Waits until `FINALIZED` is observed, then fetches a finalized receipt through the pinned v1.1.8 signature.
3. Reports `finalized` only when the receipt is `FINALIZED` and `txExecutionResultName` is `FINISHED_WITH_RETURN`.
4. Reports a finalized `FINISHED_WITH_ERROR` as failed, and missing/other execution outcomes as unknown.
5. Treats cancellation as failure, timeouts/RPC errors as unknown, and now preserves unrecognized status names as unknown rather than falsely calling them processing.

`finalizedAtObserved` is generated by the browser as the local observation time (`new Date().toISOString()`). It is **not** a chain timestamp, transaction-context timestamp, block time, or source provenance date.

## Local test evidence

Frontend unit tests use a mocked GenLayerJS client; they cover accepted/nonfinal behavior, successful finalized execution, finalized execution error, unrecognized execution result, timeout, and RPC errors. The Stage 8 change adds a regression case for an unrecognized lifecycle status. Mocked test success proves adapter branching only.

The installed transaction API was inspected from `frontend/node_modules/genlayer-js/dist/index-C3Ul1Rte.d.ts` and `dist/index.js`. No transaction was submitted or read from a network in this stage. The read-only chain identity attempts failed before any JSON-RPC response (see `V2_RUNTIME_INTEGRATION_RESULTS.md`).

## Runtime evidence not obtained

No evidence was collected for native stable Studionet acceptance/finality, execution-revert semantics, failed-write state rollback, protocol appeal rotations, idempotent child callbacks, finalized child messages, or transaction-context datetime ordering. The Stage 6 probe test's Direct Mode response is simulated and does not establish any of these properties.

Official documentation describes protocol transaction lifecycle and finality, but only an actual receipt/trace and authoritative state readback can prove behavior for this deployed application. A `FINALIZED` label alone must remain separate from successful contract execution; a CaseCourt application state such as `APPEAL_RESOLVED` also remains distinct from native transaction finality.

## Required future evidence

For each approved deployment/write, capture the transaction hash, exact environment/chain, stored and projected statuses if exposed, receipt execution result, trace/votes where exposed, and state before/after. For failure tests compare authoritative state before and after the finalized failed result. Do not resubmit after a timeout until querying the original transaction ID. No timestamp is authoritative unless its source and semantics are recorded.
